# openmlc 需求列表

本文档是《openmlc需求分析》（`docs/openmlc-requirements-analysis.md`）的配套条目化需求清单，用于模块/组件/芯片验证的需求追踪。每条需求包含编号、类别、描述、优先级、来源、验证方式与验收标准，便于后续在验证计划（Verification Plan）中直接引用和勾稽覆盖率。

## 图例

- **优先级**：P0 = 首个可用版本必须具备；P1 = 后续迭代必须具备；P2 = 增强/可选。
- **来源**：对应《openmlc需求分析》中的章节编号。
- **状态**：`待确认` = 依赖第 8 节开放问题（Q1~Q5），需求冻结前需澄清；`已明确` = 可直接进入设计。

## 1. 功能需求（REQ-FUNC）

| 编号 | 描述 | 优先级 | 来源 | 验证方式 | 验收标准 | 状态 |
|---|---|---|---|---|---|---|
| REQ-FUNC-01 | openmlc 对 cluster 内每个 L2 呈现 CHI **HN** 角色，能正确接收/响应 RN-F 发出的 REQ/DAT/RSP 通道事务 | P0 | 分析 §4.2, §5.1 | UT：单核激励回环测试；断言 CHI 状态机合法性 | 单核场景下功能与直连 HA 完全等价（golden model 对比） | 已明确 |
| REQ-FUNC-02 | openmlc 对上游 HA 呈现 CHI **RN** 角色，代表整个 cluster 发起/接收事务 | P0 | 分析 §4.2, §5.1 | UT：模拟 HA BFM，检查 openmlc 发出的事务符合 RN-F 语义 | 事务字段（Opcode/Addr/MemAttr 等）与直连场景一致 | 已明确 |
| REQ-FUNC-03 | openmlc 需为 cluster 内多个 L2 的 txnID/srcID 建立统一命名空间转换表，避免上送 HA 时 ID 冲突，并在响应返回时正确路由回发起的 L2 | P0 | 分析 §5.3 | UT：多核并发相同 txnID 值注入，检查响应路由无串扰 | 任意两个核同时使用相同本地 txnID 时，响应 100% 路由正确 | 已明确 |
| REQ-FUNC-04 | openmlc 需维护 outstanding 事务跟踪表，支持按核/按 srcID 统计当前在途事务数 | P0 | 分析 §5.3, §4.1-4 | UT：注入 N 条并发事务，读取统计寄存器核对 | 统计值与实际在途事务数一致，误差为 0 | 已明确 |
| REQ-FUNC-05 | openmlc 需将 HA 发起的 Snoop 分发给 cluster 内正确的 L2（最小可用版本：广播到所有核；进阶版本：基于 Snoop Filter 精确路由） | P0（广播）/ P1（精确路由） | 分析 §4.1-2, 开放问题 Q2 | UT：注入 SnpUnique/SnpShared，检查目标核集合 | P0：广播模式下所有核均收到且响应聚合正确；P1：精确模式下未持有该行的核不产生多余 Snoop | 待确认（Q2） |
| REQ-FUNC-06 | openmlc 需正确聚合 cluster 内多个 L2 对同一 Snoop 的 SnpResp，并按 CHI 语义生成对 HA 的单一响应（如适用） | P1 | 分析 §4.1-2 | UT：多核同时命中同一 cache line 的 Snoop 场景 | 聚合响应的一致性状态（I/SC/UC/UD/SD）符合 CHI 语义 | 待确认（Q2） |
| REQ-FUNC-07 | openmlc 需在 bypass/透明模式下可退化为纯直通（无状态转换、无额外流水线），行为与"L2 直连 HA"完全等价 | P0 | 分析 §5.3, §6 | 回归对比：bypass 模式 vs. 无 openmlc 直连基线 | 功能与时序（cycle-accurate）完全一致 | 已明确 |
| REQ-FUNC-08 | openmlc 不应终结一致性协议（不作为最终的 HN-F 数据权威），一致性终结点仍为 HA | P0 | 分析 §2.3, §5.3 | UT：检查 openmlc 不产生未经 HA 确认的 Comp/CompData | 所有面向 L2 的最终响应均可追溯到对应的 HA 响应 | 已明确 |
| REQ-FUNC-09 | openmlc 支持地址路由：可配置地址区间决定事务是否需要经过 openmlc（如 MMIO 区间旁路，一致性区间才经过 openmlc） | P1 | 分析 §5.1，参考 Top.scala 现有 `route()`/`bind()` 机制 | UT：MMIO 与一致性地址混合注入，检查分流正确 | 地址路由结果与配置表 100% 一致 | 已明确 |

## 2. 接口需求（REQ-IF）

| 编号 | 描述 | 优先级 | 来源 | 验证方式 | 验收标准 | 状态 |
|---|---|---|---|---|---|---|
| REQ-IF-01 | openmlc 面向 L2 的接口应复用仓库现有 `coupledL2.tl2chi.PortIO`（Flipped），每核一路，端口数 = cluster 内核数（参数化） | P0 | 分析 §6 | 接口宽度/信号名静态检查（elaboration-time） | 与 `chi_openllc_opt.get.io.rn(i)` 同类接口完全兼容 | 已明确 |
| REQ-IF-02 | openmlc 面向 HA 的接口应为标准 CHI RN-F `PortIO`，端口数量与聚合策略相关（默认单端口聚合，预留多端口扩展） | P0 | 分析 §5.1 | 接口宽度/信号名静态检查 | 可直接对接现有 CHILogger/route/bind 工具链 | 待确认（Q3） |
| REQ-IF-03 | openmlc 需提供 nodeID 配置输入（与仓库现有 `io.nodeID` 机制一致），用于 CHI 事务中的 SrcID/TgtID/HomeNID 字段 | P0 | 分析 §5.3 | UT：多 nodeID 配置场景下字段正确性检查 | 生成事务的 ID 字段符合配置值 | 已明确 |
| REQ-IF-04 | openmlc 需提供可观测接口（事务级日志/Trace），格式应与现有 `CHILogger` 兼容或可直接复用 | P0 | 分析 §6，历史设计沉淀 | 仿真波形/日志比对 | 日志包含 Opcode/Addr/TxnID/SrcID/时间戳，可用于离线分析 | 已明确 |
| REQ-IF-05 | openmlc 需提供性能计数器接口（outstanding 数、各类型事务计数、平均/尾延迟），供 checker/scoreboard 读取 | P0 | 分析 §7 | UT：与软件参考模型统计值对比 | 计数器误差为 0（周期精确） | 已明确 |
| REQ-IF-06 | openmlc 需提供控制/配置接口（延迟注入强度、Retry 注入概率、Snoop 时延整形参数等），支持仿真期动态配置 | P0 | 分析 §4.2, §5.1 | UT：配置不同参数值，检查行为按配置生效 | 注入行为的统计特征（如平均延迟）与配置值偏差 < 5% | 已明确 |
| REQ-IF-07 | openmlc 需暴露与 `io.l3Miss`/Top-Down 监控类似的旁路信号（可选），用于向 core 侧反馈 cluster 级性能事件 | P2 | 分析 §7，参考现有 `io.l3Miss` 机制 | UT：功能对比 | 与现有 Top-Down 监控框架兼容 | 已明确 |

## 3. 性能/时序需求（REQ-PERF）

| 编号 | 描述 | 优先级 | 来源 | 验证方式 | 验收标准 | 状态 |
|---|---|---|---|---|---|---|
| REQ-PERF-01 | bypass 模式下引入的额外流水线深度应可配置为 0（组合直通）或固定小整数（如 1~2 级） | P0 | 分析 §6, REQ-FUNC-07 | 时序仿真对比 | 配置为 0 时与直连基线时延差为 0 cycle | 已明确 |
| REQ-PERF-02 | 非 bypass（验证特性开启）模式下，openmlc 自身引入的固有延迟应可量化、可配置，且不应随 cluster 核数增长而非线性放大 | P1 | 分析 §4.1-4 | 不同核数配置下的延迟扫描测试 | 延迟随核数增长应为常数或线性，非指数级 | 已明确 |
| REQ-PERF-03 | openmlc 的 outstanding 跟踪表容量应可配置，且在容量耗尽时的行为（拒绝新请求/RetryAck/阻塞）需明确定义并可验证 | P0 | 分析 §4.1-4 | UT：容量边界压力测试 | 容量耗尽时行为与配置策略 100% 一致，无死锁 | 已明确 |
| REQ-PERF-04 | openmlc 需支持按核（srcID）粒度的反压隔离能力（即一个核的拥塞不应无条件阻塞其他核），至少提供可开关的隔离模式用于对比研究 | P1 | 分析 §4.1-3, §4.1-6（公平性/QoS） | UT：单核注入拥塞，观测其余核时延分布是否受影响 | 隔离模式开启时，非拥塞核的 P99 时延劣化 < 10% | 已明确 |

## 4. 一致性/协议正确性需求（REQ-COH）

| 编号 | 描述 | 优先级 | 来源 | 验证方式 | 验收标准 | 状态 |
|---|---|---|---|---|---|---|
| REQ-COH-01 | 在 HA 侧发生 Retry（RetryAck/PCrdGrant 流程）时，openmlc 需正确处理重试语义，不产生重复事务或事务丢失 | P0 | 分析 §4.1-1 | UT：HA BFM 注入 RetryAck 场景，检查事务最终一致完成 | 100% 事务最终完成且无重复/丢失 | 已明确 |
| REQ-COH-02 | 在 Snoop 拥塞（HA 侧 snoop 队列积压）场景下，openmlc 不应引入死锁或活锁 | P0 | 分析 §4.1-2, §4.1-5 | 形式化/断言验证 + 长时间随机压力测试（>10^6 事务） | 无死锁/活锁断言触发；所有事务在有限时间内完成 | 已明确 |
| REQ-COH-03 | openmlc 需保证跨核数据一致性：任意时刻，同一 cache line 在 cluster 内多个 L2 之间的状态（I/SC/UC/UD/SD）符合 CHI 一致性语义 | P0 | 分析 §4.1-5 | UT + 随机压力测试，结合参考模型（golden reference）比对 | 与参考模型状态 100% 一致 | 已明确 |
| REQ-COH-04 | 对于要求 Order 的事务（如 DVM、Ordered transaction），openmlc 不应破坏 HA 侧要求的顺序语义 | P1 | 分析 §4.1-5 | UT：Ordered 事务序列注入，检查完成顺序 | 完成顺序与 CHI Order 字段语义一致 | 待确认（Q1，取决于 CHI Issue 版本对 Order 的具体要求） |

## 8. 待澄清后需要新增/修订的需求

以下事项对应《openmlc需求分析》第 8 节开放问题（Q1~Q5），一旦澄清将直接影响本清单中标记为"待确认"的条目，并可能新增需求：

| 开放问题 | 潜在影响的需求编号 |
|---|---|
| Q1 HA 具体来源与 CHI 协议版本 | REQ-COH-04, REQ-CFG-02, REQ-VER-01 |
| Q2 是否要求精确 Snoop Filter | REQ-FUNC-05, REQ-FUNC-06 |
| Q3 openmlc 与 openllc 的拓扑关系（并列 vs. 串联） | REQ-IF-02, 可能新增地址/nodeID 分配类需求 |
| Q4 故障注入场景清单的优先级划分 | REQ-VER-01, 可能新增更多 REQ-IF-06 子场景 |
| Q5 cluster 核数上限 / 多 cluster 级联需求 | REQ-CFG-01, 可能新增多级拓扑类需求 |

建议在需求评审会议上逐项确认 Q1~Q5，确认后更新本清单的"状态"列，并将本文档作为验证计划（Verification Plan）的直接输入。
